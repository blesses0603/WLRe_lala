# LaLa 全新重製規劃（桌面版）

> 狀態：規劃階段；本文件不代表已開始實作、功能已完成或通過測試。
> 基準：main 的 v0.6.1 開發版。舊版僅作為功能行為、協定與資源來源的參考，不直接沿用舊 UI／架構作為新產品骨架。

## 1. 重製目標

- 從頭建立全新 LaLa 桌面版，並與 Android 版同步規劃。
- 使用深藍科技風格，建立一致的設計系統與清楚的操作層級。
- 優先重建「戰鬥（Battle）」與「地圖（Map）」。
- 保留舊版已驗證的協定、安全檢查與伺服器確認原則；不因重寫而推定舊功能均已驗證。
- 新舊程式分離開發，避免重製中的變更影響現有可用版本。

## 2. 舊版盤點原則

開始實作前，逐模組盤點：
1. 功能入口、使用流程與 UI 狀態。
2. 網路封包／協定、請求與回應配對、逾時及重連行為。
3. 官方資料、資源版本、快取與信任來源驗證。
4. 設定檔、帳號／伺服器隔離及敏感資料處理。
5. 自動化操作的前置條件、伺服器確認與錯誤恢復。
6. 現有測試、未覆蓋情境及正式服 E2E 證據。

每項功能標記為「已確認」「待驗證」「不移植」，並記錄證據；不直接複製未理解的舊實作。

## 3. 目標架構（提案）

- **UI 層**：頁面、元件、狀態呈現與使用者操作。
- **Application 層**：戰鬥、地圖等用例與工作流程。
- **Domain 層**：角色、隊伍、戰鬥狀態、地圖座標及領域規則。
- **Protocol／Infrastructure 層**：連線、封包編解碼、資源載入、日誌與持久化。
- **Shared contracts**：與 Android 共用的協定模型、領域規則及測試案例；平台 UI 與生命週期分開實作。

新架構的具體語言、UI toolkit 與打包方式，應在完成依賴盤點及技術驗證後決定，不預先假定整體技術棧。

## 4. 分階段交付

### Phase 0 — 盤點與規格
- 建立舊版功能／模組／資源／測試清單。
- 繪製 Battle、Map 現有流程與協定序列。
- 確認桌面端目標作業系統、封包邊界、資料安全及可重用的跨平台核心。
- 交付：功能矩陣、架構決策紀錄（ADR）、風險清單、驗收案例。

### Phase 1 — 新專案骨架與設計系統
- 建立獨立的新程式入口、設定與日誌策略。
- 定義深藍色彩、字體、間距、元件狀態、視窗縮放與無障礙對比。
- 建立登入／連線狀態與錯誤呈現基礎。
- 驗收：乾淨環境可建置啟動；錯誤與斷線狀態可復原；不影響舊版。

### Phase 2 — Battle 戰鬥模組（優先）
- 先完成戰鬥狀態模型與協定測試，再建置 UI。
- 分離角色／夥伴狀態、隊伍與陣形、目標、技能／普攻、戰鬥紀錄。
- 自動操作必須有明確啟停狀態、前置條件、伺服器回覆確認及失敗保護。
- 驗收：封包／模型測試、錯誤回應與逾時測試、手動操作流程、可重現的回歸測試。

### Phase 3 — Map 地圖模組
- 分離地圖畫布、座標與場景狀態、移動控制、路徑／傳點資料及同步服務。
- 區分已驗證的官方資料與舊版參考資料；未驗證傳點不可標示為可用。
- 驗收：座標更新、場景切換、移動取消、失聯復原與資料版本檢查。

### Phase 4 — 其他功能逐步移植
- 依盤點結果安排帳號／角色、背包、技能、夥伴、社交、紀錄與其他模組。
- 每個模組獨立交付，附回歸測試與資源來源說明。
- 未完成驗證的功能明確標示，不以 UI 完成代替功能完成。

### Phase 5 — 整合、回歸與發佈候選版
- 執行跨模組整合測試、平台建置測試、安全檢查及可用性驗收。
- 建立可重現的打包流程、版本資訊、校驗碼與回復方案。
- 未通過必要驗收前，不建立正式 Release／Tag。

## 5. 品質與安全門檻

- 不把 UI 狀態當作伺服器已成功執行的證據。
- 對重要操作採請求／回應確認、逾時、去重及可恢復錯誤處理。
- 帳密與 Token 不得寫入日誌或硬編碼；敏感資料採最小權限保存。
- 官方資源與版本須驗證來源、格式及完整性。
- 每階段執行對應單元測試、整合測試及回歸測試，明確區分模擬測試與正式服 E2E。
- 不刪除舊版資源，除非已確認無引用、替代來源等價且通過回歸測試。

## 6. 目前尚待確認／驗證

- 桌面版新程式的最終技術棧與支援作業系統。
- Battle、Map 各流程的完整協定與正式服驗收證據。
- 舊版哪些資源可合法、可靠且可追溯地作為新版本資料來源。
- 新舊版並行測試、設定遷移與未來版本發布策略。
