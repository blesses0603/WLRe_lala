## 商店、一般道具與協力修正（2026-11-11）

依使用者指定，**交易所、星盤覺醒、角色與夥伴裝備穿脫暫不實作**。本批完成下列電腦版操作與公用核心流程；後面的 Lua 缺口表保留核對當時的狀態，現況以本節為準。

- NPC 武器／道具商店在目前 S20-6 選單中顯示商品、單價、數量與合計；確認後送出官方 C27-1。意圖綁定場景、互動索引、effect 封包、商品索引、ID 與顯示價格，寫入前再檢查角色、資源、背包、金幣及選單。

- 背包加入一般消耗道具的單次使用、角色／夥伴對象、手動販售、丟棄及名稱／數量排序。販售與丟棄先顯示名稱、數量、金額或不可復原提示；確認期間的舊物品身分不會換成新格位。排序只調整顯示，不發送未核對的整理封包。
- 一般使用採官方 C23-15，核對使用回覆及同一物品實際扣除。僅開放已分類的一般消耗分支，檢查開放旗標、用途、等級、對象、友好度、死亡／復活用途及保留／鎖定／期限。`ItemData` 同版解析補讀官方性別／使用對象限制欄位。裝備、需要專屬介面的道具及尚未能唯一分類的特殊物品不會落入通用使用；不能將此入口解讀成所有特殊道具系統已移植。

- 協力建房不再把 `SellDataId` 當入場費；保留人數、等級、房間等檢查，補上隊伍、小屋、一般副本房間與未領協力獎勵的阻擋。免費寶箱預檢改為官方兩個空格；需獎勵明細與實際入包，單純寶箱關閉不視為已領到物品。

## 戰鬥／徘徊接續與小地圖雙擊移動

- 戰鬥先依目前場次、回合與格位順序規劃所有存活的本機／夥伴單位，再透過帳號通道連續送出；規劃過程預留共用物品數量。已送格位由獨立 guard 保存，即使顯示用 commands 被替換或 AI 重開，也不重送。同一回合只更新一筆操作結果。更正先前口頭說明：原 C# 單位下令已是 `AwaitAcknowledgement=false`，本批補的是整輪規劃與資源協調，不是取消不存在的逐單位回覆等待。
- 本機角色真正退場後，依 Python `SessionLogic` 等待 2.5 秒，才消耗一次戰後 C20-6 許可；協力剩餘場數大於一且已證明己方獲勝時等待 5 秒。未知場數使用 2.5 秒，不推算勝負。重複退場通知不重設計時；S20 許可與退場計時合併為一次接續。新角色／場景撤銷舊計時，S20-8 才放行戰後後續功能。
- 戰後依保存的 AI 設定先等待背包穩定 0.5 秒，再修理／整理、野外補給，最後恢復徘徊。修理要求同一裝備恢復及道具耗用兩項實際證據；整理要求同格位、同數量的販售／丟棄回覆及背包扣除。鎖定、限時、保留格位與指定修復／補給道具受保護；工具不足暫停徘徊，結果不明不重送。預設修理／整理開關仍關閉。

## 事件同步與紀錄洗版修正

主畫面的「接續遊戲事件」原本仍由戰鬥 AI 處理，開啟 AI 因而補跑等待中的一般事件；每一步再附加「正在送出／等待確認／已收到更新」三行紀錄。這些行數不能作為攻擊封包重送的證據，但事件同步所屬流程與顯示方式確實不妥。

- 一般事件接續改由帳號生命週期所屬的單一背景工作處理，需角色、世界初始化、資源及伺服器新許可均有效；開關戰鬥 AI 不會啟動、重播或取消它。手動 NPC 對話不自動接續。
- 此私有工作可以在一般操作等待確認時回覆必要事件，避免出口等操作等待事件、事件又等待操作通道的死鎖。所有實體寫入仍走帳號傳送鎖，保留批次邊界、同角色／場景／資源核對與單次許可消耗。它不覆蓋一般操作的 Pending 狀態。
- 一般操作各階段更新同一筆歷史；一段核心事件同步維持一筆進度與步數，收到事件結束才標示完成。不同操作保留各自結果，已送出但未確認的錯誤不重試、不被成功摘要覆蓋。
- 桌面將連續事件接續通知／事件更新合併顯示；拒絕及其他角色自身資料仍各別顯示。只改呈現，不刪除接收端回覆證據，不停收必要資料。

## 確認並修正的接收缺口

1. **登入完成後的必要確認缺失**：收到自己角色的 S7／S12 定位後，換地圖先回 C12-1，再回 C3-2；同地圖回 C3-2。其他角色定位不觸發本機確認。
2. **操作回覆被短紀錄擠掉**：原操作確認從最近 500 筆 metadata 補讀；NPC 流量可先擠掉關鍵回覆。本次改成操作期間由接收端即時折疊所需回覆，等待端讀取折疊結果；不擴大原始封包儲存，不依賴畫面篩選，也不重複計算回覆。
3. **接續許可也不能依賴短紀錄**：S20 許可保存自己的封包編號及撤銷狀態；UI 暫停／重新啟動不能重用已消耗許可，換正式連線則不沿用舊序號。
4. **逐 byte 解框及鎖定成本**：原正式接收為保留錯誤前有效封包，每 byte 呼叫一次 Feed 並鎖定。本次改為一次處理到單一完整 frame，仍保留後段 frame 損壞前已完成的提交；分包、合包、最大 frame 及 EOF 檢查不放寬。
5. **接收半批就下令**：發布的批次狀態供規劃及實際寫入核對；批次標記不增加伺服器封包數、不偽造新的 server revision，也不靠 UI 是否刷新判斷。
6. **角色更新後仍以舊身分回應**：伺服器新的 S3 身分會更新定位確認對象、清除舊許可及舊角色顯示紀錄；不把另一角色定位當成本機確認。未知的零角色 ID 不開放一般操作。
