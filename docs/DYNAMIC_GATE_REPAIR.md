# 動態 Runtime 檢查與製作解析修正

本次修正畫面中「官方已更新／固定 1275」、「解析 6／7，製作待處理」及舊式 ZIP 提示混用的問題。

## 製作

同步資料庫原先沒有呼叫製作解析器或保存 smith_rows；畫面又將「候選已解析」排除於完成數之外，不能僅由 6／7 推定官方製作資料格式不相容。

目前從實際 SmithData_C 原始表辨識已審核的 33／35 bytes 格式，完整保留新版 recipe_id（含相同產物的多份配方），寫入版本化 smith_v1 解析紀錄，保留新增／異動／移除比對。未知格式仍保留原始表並記錄 parse_failed，不能冒充已解析；不會阻止其他表的解析。資料庫唯讀配方介面與正式動態 Runtime 使用同一格式選擇函式。解析狀態七項統一按 status=parsed 計數。

既有快取會在下一輪 Launcher 同步使用原始資料重新解析、更新報告；不需要刪除使用者資料庫或重下載所有 Bundle。

## 官方版本與畫面

一般 GUI 檢測不再呼叫固定 1275 的 ready()。當次官方 MainPackage／DataPackage 可為不同版本；完整 Runtime 必須自行驗證官方 Manifest、Bundle、Schema、前後版本一致性，並再次核對預登入取得的 DataVer、ExeVer 及完整雙包識別。

資料通過後狀態為 protocol_pending，顯示「官方資源已驗證 · 遊戲協定待驗收」。缺少或無法解析目前 Runtime 時另列 runtime_unavailable；官方回應不足與新版客戶端也有獨立狀態。舊式 ZIP 補充稽核不再混入目前官方版本畫面，原有診斷報告仍可供維護者查看。

重要邊界：本次沒有正式服登入帳號或協定端到端驗收證據。資料通過不自動核准遊戲封包，遠端自稱或可編輯資料庫／Launcher 紀錄也不能核准登入。最新協定未驗收時仍禁止登入，但不再錯稱官方資源版本不支援。歷史 baseline 只保留給明確指定 sources/checker 的離線測試介面。

## 回歸範圍

新增／更新測試涵蓋 33／35 bytes 真實形狀配方、同產物不同配方、版本差異、未知格式與其他表獨立保存、七項進度、不同官方雙包版本、Manifest 重新發布識別變更、離線／缺表／不完整官方回應、新客戶端、偽造協定核准及 GUI 提示。三平台 CI 會重新執行；提交時不把尚未完成的 CI 或正式服 E2E 標記為通過。
