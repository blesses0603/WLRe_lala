## 第 02 階段：靜態表解析

官方 Lua 原始碼可核對 **格式**，不等於已取得二進位表 **內容**。目前提供嚴格解析：

- `DungeonData_C`：副本 ID、類型、難度／分組、地圖 ID、NPC、16 格獎勵與加倍／特殊旗標。
- `CooperateEventData_C`：協力種類與描述 ID、場次、標記、四個指定夥伴與額外獎勵。
- `ScenesData_C`（由 `StageData:New` 解析）：場景文字 ID、最低等級、最少／最多人數、時間限制與房間數。

來源：上傳的 `WLRE_Lua_1262_Decoded_Analysis(1).zip` 中 `Lua/Data/{DungeonData,CooperateEventData,StageData,AwardData}.lua`。透過 `wlre.services.instance_catalog.catalog(dungeon, cooperative, scenes, names)` 提供已抽出的原始表位元組。對無法取得的表與文字不建立假資料，不自行推測名稱、開放狀態或獎勵。

## 後續實施準則

## 2026-10-19 已上傳 ManifestFiles 解析結果（1262）

使用者提供的 `DataPackage_1262.rar`（只含 16,830 位元組的 Manifest）與
`MainPackage_1262.rar`（只含 2,549,190 位元組的 Manifest）均可讀取，
**但均不含實際的 `BundleFiles/**/__data`**。因此目前無法產出官方副本名稱表。

1262 `Lua/Logic/Data.lua` 明確呼叫
`GameDataList["ScenesData_C"] = this.OnLoadSceneData`，而
`OnLoadSceneData` 逐筆呼叫 `StageData:New(binaryReader)`。
因此 **`ScenesData_C` 才是 `parse_stages` 的輸入**，並非 `StageData_C`。

上述 hash 來自 `DataPackage` 官方 Manifest 的 bundle 表，用以定位安裝路徑：
`<遊戲>_Data/yoo/DataPackage/BundleFiles/<hash前兩碼>/<hash>/__data`。
不應把 Manifest `.bytes` 當成表本身，也不應自行生成不存在的官方名稱。

## 第 03 項：加入／離開副本房間（2026-10-19）

### 加入房間
- **一般副本**：手動更新並選取 S85-1 的 `roomId + SN`（SN 不可自行編造）；公開與私人 C85-5 按原版帶入密碼 uint16。S85-3 code 0 僅表示伺服器接受請求，須收到 S85-5 kind 1 且 `roomId` 相符才完成。
- **協力**：選取 S186-17 的 `roomId`，C186-4 帶 uint32 密碼；要求按下確定承認可能消耗門票或點數。S186-2 code 10 表示加入且扣點成功，仍需 S186-3 的 `IsJoin`、房間 ID 與本機角色成員資料才完成。
- 房間清單必須在 **120 秒內**收到；沒有最新清單或 SN 不符，直接拒絕，UI 不提供任意輸入房號。
- 私人房間要求 **四位 ASCII 數字密碼**；只在單次手動指令內傳遞，不存入 `State`、診斷日誌或設定檔。

### 離開房間
- 一般副本在伺服器同步的等待階段可送 C85-6，等待 S85-5 kind 2／4 或本人 S85-12 確認。
- 協力在已有房間且未進入準備／配對時可送 C186-5，等待 S186-13 確認。準備取消（C186-7）將由第 04 項建構，不假設可以無條件退出。
- GUI 的「加入房間／離開房間」均要求使用者再次確認，送出後本機停用該按鈕直到伺服器狀態更新。

### 不確定結果與流程隔離
- 兩個模式之間的 `create_pending`、`join_pending`、`leave_pending` 以及 `*_uncertain` 相互阻擋，避免在未確認時又開房、加房或離房。

## 第 04 項：協力準備／取消準備，不指定夥伴（2026-10-19）

**需求更新：使用角色原本正常出戰的夥伴。** 不要求指定夥伴，不提供副本專用換寵設定；出戰狀態仍由既有的 `S19`／`knowledge.active_npc_id` 管理。即使目前沒有出戰夥伴，也不自動派遣其他夥伴。

核對 1262 `Lua/UI/Logic/UICheckPlayerList.lua` 與 `CooperateEventManger.SendSetStatus()`：

- **只有房主**（`MyRoom.Member[1].ID == Role.playerRoleId`），並且**房內人數已達 MaxPlayerCount**，才能按準備／取消準備。
- 操作只送 `C186-7: roomId(uint16) + status(uint8)`。準備為 1、取消為 0；**不含夥伴 ID**。
- 準備可能立即開始協力配對／挑戰，點擊按鈕後仍須玩家再確認一次，程式不自動替玩家點擊。
- `S186-3` 的同一房間 `IsStandby` 才算狀態確認；`S186-20` 是配對狀態通知，不單獨視為指令執行成功。
- 加入／離開／創房／協力準備共用跨模式未確認操作鎖；**20 秒逾時或斷線不能盲目重送**，防止重複配對。
- 畫面只唯讀顯示 `active_npc_id`，協力準備既不呼叫 `companion_command`，也不發 C19-1／C19-2 出戰／休息指令。
- 官方 `UIDungeonPartner.TryOpen` 只為「指定夥伴額外獎勵」提供可選提示，與 C186-7 準備狀態無關。1262 已提取兩筆活動的追隨 NPC ID 與額外獎勵種類均為 0，故不需要這個提示；若未來更新官方額外獎勵，不保證自動享有加成。
- `tests/test_instance_standby.py` 涵蓋正式封包、滿員／房主、S186-3、S186-20、超時與斷線、跨模式保護、UI 操作及既有出戰夥伴完全不變。

## 第 07 項：權威完成判定、協力連戰與免費獎勵（2026-10-19）

### 官方 1262 協定
- 一般副本只有 S85-15（Dungeon.CompleteDungeon）或新式副本 S85-21-100 代表副本完成，沒有可直接強制通關的客戶端封包。戰鬥 winner／擊殺及倒數不等於完成。
- 協力 S186-15 提供 FightCount。官方 FightManager 在多場協力戰且有勝負通知時，會以 UICooperateWait 等待 5 秒再呼叫一般事件 C20-6 00；其餘已知場次維持安全的戰後延遲。LaLa 只從伺服器取得場次與回覆，不送虛構續戰封包。
- S186-11：RewardCount／WinStage／OpenReward／RewardMark／RewardNPCMapID；OpenReward=1 免費，OpenReward=2 付費；RewardMark bit 0 是一般獎勵，bit 1 是指定夥伴獎勵。
- C186-10：領取免費寶箱，零 payload。S186-10：最多四筆 AwardData，每筆 kind:uint8、id:uint32、value:uint32，固定 9 bytes；零獎品回覆不冒充實際領取成功。背包入庫仍待 S23 權威同步。
- C186-21：取消獎勵，零 payload，只能由玩家二次確認手動發送；需 S186-11 OpenReward=0 才算伺服器確認。付費寶箱沒有經核對的自動購買流程，絕不自動購買或扣點。

### 自動免費領獎保護
- 預設關閉、必須使用者明確開啟，僅當次登入有效，不跨帳號或重連保存。
- 僅當 S186-11 表示免費且一般獎勵標記存在、角色與伺服器狀態可靠、背包資料已同步並且保守具有四個空位、無物品預留或尚未確認之副本操作時，網路排程才發一次 C186-10。
- 同一獎勵快照以 fingerprint 去重，不會因重複推送再次要求；伺服器 OpenReward=0 確認寶箱關閉後才允許新一輪獎勵。
- 25 秒無回覆、斷線或領獎期間被退出房間均會標記結果不明並禁止重送。需要重新登入同步確認；付費寶箱不自動取消，也不自動買入。
- GUI 協力頁新增免費領取、放棄寶箱、自動領取開關與狀態說明；一般副本只顯示伺服器完成狀態，無虛構領獎按鈕。
- 不改既有出戰夥伴、不新增 C19-1／C19-2、不啟用掃蕩 C85-16（可能消耗道具），也不自動啟用戰鬥 AI。
